Make managed Substrate materialization visible

Managed Substrate checkout materialization on the Stem is silent on success, so a slow clone appears as a hung system. This slice introduces logging to make the wait visible.

1. **Before the loop** — Logs the total number of managed Substrates being materialized to turn the silence into an expectation. If none are configured, a distinguishable no-op line is logged.
2. **Per Substrate, before the work** — Logs which Substrate is being materialized.
3. **Per Substrate, after the work** — Logs whether the Substrate was cloned or refreshed. We determine this by checking if the `managedCheckoutDir` exists prior to calling `cloneNamedForeignSubstrate`, preserving the function's signature.

**Out of scope for this slice:**
- **Blocking versus concurrent startup:** We leave materialization blocking. Not materializing before the listener comes up means a first delegated call can race a half-materialized checkout. That trade deserves its own issue rather than riding along with a logging change.
- **Service-manager start timeout:** TimeoutStartSec inherits the default, so a large enough first clone can exceed it. This slice makes the wait visible (which is worth having on its own) but does not remove the timeout risk.

### Mutations verified
1. Counting all Substrates rather than only managed ones correctly failed `TestMaterializeManagedCheckoutsLogging`.
2. Reporting "cloned" unconditionally correctly failed the same test on the refresh run.
3. Dropping the no-op line correctly failed the 0-managed Substrates case.
